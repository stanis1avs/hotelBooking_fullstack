# Функциональность и эксплуатация

## Сценарий работы приложения

Описано с точки зрения гостя — что он делает и что при этом происходит в системе.
Дальше то же для менеджера и администратора.

### Поиск

Страница открывается витриной: изображение, заголовок с реальным числом отелей
в каталоге и форма поиска — название или город и даты проживания.

Под формой два ряда подборок. Верхний — направление: к морю, в горы, в город,
за город, на лыжи. Нижний — удобства: Wi-Fi, парковка, завтрак, бассейн, СПА,
с питомцем. Это условия запроса к базе, а не подстановка текста в поиск.
Логика у рядов разная и намеренно: направления складываются по **ИЛИ** — гость
смотрит и море, и горы; удобства требуются **все сразу** — отметив бассейн и СПА,
он хочет отель, где есть оба.

Выдача учитывает занятость на выбранные даты: отель, где на период не осталось
ни одного свободного номера, в неё не попадает. Если свободных не больше трёх,
карточка говорит об этом прямо — «остался 1 номер на эти даты». Цена показана
и за весь срок, и за ночь.

### Бронирование

Страница отеля ведёт тремя шагами: даты → выбор номера → подтверждение.
Второй шаг показывает только свободные на период номера: у каждого площадь,
вместимость, тип кроватей и цена за весь срок, а снимок открывает галерею
с миниатюрами и перелистыванием.

Последний шаг — сводка: отель, номер, даты, число ночей, итог, контакты гостя
и пожелания к заселению.

Пересечение дат отклоняет сервер, а не только интерфейс, — там же отклоняются
даты задним числом и снятые с продажи номера.

Оговорка по-честному: проверка устроена как «посмотреть, нет ли пересечения,
затем вставить». Уникальным индексом пересечение интервалов не выразить,
а транзакции требуют replica set, которого в текущей сборке нет. При двух
одновременных запросах на один номер остаётся узкое окно, в которое пройдут оба.
Для нагрузки пет-проекта это приемлемо, для боевой системы понадобится
транзакция или блокировка на уровне номера.

### Мои брони и поддержка

Гость видит свои брони и может их отменить — чужую отменить нельзя, владельца
сверяет сервер.

Поддержка: обращение создаётся одним полем, дальше идёт переписка с менеджером.
Непрочитанные ответы видны отметкой на пункте меню; она гаснет, когда переписку
открыли. Закрытое обращение новых сообщений не принимает — нужно создать новое.

### Что видит менеджер

Дашборд за 30 дней: выручка, число бронирований, предстоящие заезды и проживающие
сейчас. Под каждым числом — динамика к тому же периоду прошлого месяца и спарклайн
за период; клик по плитке фильтрует таблицу под ней.

Таблица всех броней: сортировка по колонкам, страницы, отмена брони. Статус
проживания («предстоит», «проживает», «завершена») выводится из дат — отдельного
поля под него в модели нет.

Плюс очередь обращений: ответить и закрыть.

### Что видит администратор

Отели и номера: создание, правка, загрузка фотографий, удаление. Формы открываются
диалогом. Удаление мягкое — запись пропадает из поиска, но история броней остаётся
читаемой, а не ломается ссылкой в никуда.

Пользователи: список с поиском по имени, почте и телефону, фильтр по роли, создание
учётной записи и правка имени, телефона и роли. Свою роль изменить нельзя, иначе
единственный администратор способен случайно остаться без доступа. Смена роли
пишется в журнал как изменение прав.

## Запуск

Скопируйте `.env.example` в `.env` (в корне) и заполните значения.
Для локального запуска бэкенда те же ключи нужны в `hotelBooking_nest_back/.env`.

### Вариант 1: всё в Docker

```bash
docker compose up -d --build
```

Приложение — http://localhost:4200. Внутри поднимаются MongoDB, бэкенд и nginx,
который отдаёт фронтенд и проксирует `/api`, `/graphql` и WebSocket на бэкенд.

### Вариант 2: локально, для разработки

```bash
# терминал 1 — база
#   Windows: служба MongoDB уже запущена, ничего делать не нужно

# терминал 2 — бэкенд
cd hotelBooking_nest_back && npm run start:dev

# терминал 3 — фронтенд
cd hotelBooking_angular_front && npm start
```

Фронтенд — http://localhost:4200, бэкенд — http://localhost:7000.

**Для активной разработки используйте второй вариант.** В Docker нет горячей
перезагрузки: каждое изменение кода требует пересборки образа.

## Перезапуск после изменений

Docker не подхватывает изменения кода сам.

| Что поменяли | Команда |
|---|---|
| Код фронтенда | `docker compose up -d --build frontend` |
| Код бэкенда | `docker compose up -d --build backend` |
| И то и другое | `docker compose up -d --build` |
| Только переменные в `.env` | `docker compose up -d --force-recreate` |
| Ничего, просто перезапустить | `docker compose restart backend` |

После пересборки фронтенда обновите вкладку через **Ctrl+Shift+R**: имя
CSS-бандла меняется, но браузер может отдать старый файл из кэша.

```bash
docker compose logs -f backend     # логи бэкенда в реальном времени
docker compose ps                  # что запущено и на каких портах
docker compose down                # остановить (данные в томе сохранятся)
docker compose down -v             # остановить И УДАЛИТЬ базу — необратимо
```

## Команды

| Команда | Что делает |
|---|---|
| `npm run start:dev` | Бэкенд с автоперезагрузкой |
| `npm run build` | Сборка бэкенда в `dist/` |
| `npm test` | Тесты бэкенда |
| `npm run lint` | ESLint с автоправкой |
| `npm start` | Фронтенд на `localhost:4200` |
| `npm test` | Тесты фронтенда (в каталоге фронтенда) |
| `npm run build` | Прод-сборка фронтенда |
| `node scripts/backfill.js --demo` | Заполнить недостающие поля отелей и номеров |

Оба скрипта идемпотентны и понимают `--dry`: показать, что изменится, ничего не трогая.

## Тесты

**Бэкенд** — 24 теста на Jest: провайдеры пользователей, бронирований и отелей плюс
пороги защиты GraphQL. Покрыто то, что чинилось: повторная регистрация одного адреса,
экранирование спецсимволов в поиске, ограничение выборки ролью, запрет менять себе
роль, пересечение дат и даты задним числом, бронирование снятого с продажи номера,
чужая бронь при удалении, занятость отеля по реальному числу номеров, логика
фильтров «ИЛИ» для направлений и «И» для удобств.

**Фронтенд** — 17 тестов на Vitest: редьюсеры и утилиты дат.

```bash
cd hotelBooking_nest_back && npm test
cd hotelBooking_angular_front && npm test
```

## Данные

База в Docker и локальная MongoDB — **разные и не синхронизируются**. Контейнерная
живёт в томе `hotelbooking_fullstack_mongo-data` и переживает `docker compose down`.

Перенести локальную базу в контейнер:

```bash
docker run --rm --network hotelbooking_fullstack_default \
  -e SRC="mongodb://host.docker.internal:27017/nest" \
  -e DST="mongodb://ЛОГИН:ПАРОЛЬ@mongodb:27017/?authSource=admin" \
  mongo:7 sh -c 'mongodump --uri="$SRC" --archive | mongorestore --uri="$DST" --archive --nsInclude="nest.*" --drop'
```

Логин и пароль — значения `DB_NAME` и `DB_PASSWORD` из корневого `.env`.

Фотографии лежат файлами в `uploads/`, в документе хранится путь. Имя файла — хеш
содержимого: одинаковые изображения занимают место один раз, а при изменении файла
меняется и имя, поэтому статику можно отдавать с годовым сроком жизни кэша.

## Первый администратор

Учётные записи для демонстрации создаются локально и в репозиторий не попадают.

```bash
# зарегистрируйте клиента через интерфейс, затем повысьте роль в базе
mongosh nest --eval 'db.users.updateOne({email:"you@mail.ru"},{$set:{role:"admin"}})'
```

Дальше пользователей с любой ролью можно заводить в разделе «Пользователи».

## Переменные окружения

Полный список с комментариями — в [`.env.example`](.env.example). Ключевые:

| Переменная | Смысл |
|---|---|
| `MONGO_URI` | Строка подключения к базе |
| `DB_NAME`, `DB_PASSWORD` | Учётные данные MongoDB в контейнере |
| `SERVER_PORT`, `CLIENT_PORT` | Порты бэкенда и фронтенда |
| `CORS_ORIGINS` | Разрешённые источники через запятую |
| `JWT_TOKEN_SECRET` | Секрет access-токена |
| `JWT_REFRESH_SECRET` | Секрет refresh-токена — **обязан отличаться** от предыдущего |
| `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` | Сроки жизни токенов |
| `COOKIE_SECRET` | Подпись cookie |
| `GRAPHQL_MAX_COMPLEXITY` | Потолок стоимости GraphQL-запроса, по умолчанию 1000 |

Секреты генерируются так:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Если `JWT_TOKEN_SECRET` и `JWT_REFRESH_SECRET` совпадут, refresh-токен будет
приниматься как access-токен.

## Масштабирование

Приложение рассчитано на один экземпляр бэкенда. В памяти процесса держатся две
вещи: счётчики ограничения частоты запросов и состояние соединений Socket.IO.

На одном процессе это работает. Со второго — счётчики попыток разъедутся (пять
попыток входа в минуту превратятся в пять на каждый процесс), а сообщения чата
не дойдут до тех, кто подключён к другому узлу. Тогда понадобится общее хранилище:
Redis для счётчиков и `@socket.io/redis-adapter` для сокетов. Раньше этого момента
Redis не решает ни одной существующей задачи.

Отзыв refresh-токенов в память не попадает: записи лежат в коллекции `revokedtokens`
с TTL-индексом по `expiresAt`, и Mongo удаляет их сама, когда истекает срок самого
токена. Так отзыв переживает перезапуск и общий для всех процессов — на втором
экземпляре он продолжит работать без изменений.
